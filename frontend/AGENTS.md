## 컴포넌트 및 UI 구현 및 수정

메인 에이전트는 컴포넌트 및 UI 구현·수정을 `component_worker`에 위임하고, 1차 구현이 끝나면 `uiux_reviewer`를 호출하세요. 점검과 피드백 전달은 `docs/UIUX-guide.md`를 따르세요.


## Storybook 테스트

컴포넌트를 새로 만들게 되어 스토리북을 만들거나, 스토리북을 만들어달라는 직접적인 요청이 들어온다면 다음 사항을 준수하여 스토리북을 만들어주세요

1.컴포넌트 하나에 대해 mdx 문서를 작성하세요. 해당 문서내에는 다음과 같은 내용이 있어야 합니다.

- 컴포넌트 명
- 컴포넌트에 대한 요약
- props에 대한 설명 (만약 tailwind variant props가 인자로 있는 경우 그 variant props에 대한 설명도 곁가지로 있어야 함)
- 사용 예시

문서 한글로 써주세요 ㅠㅠㅠㅠㅠㅠㅠㅠㅠㅠㅠ

2. 컴포넌트 props에 따라 기본 렌더링(default)를 만든 뒤, 시각적으로 바뀔 수 있거나 버그가 발생할 확률이 높은 경곗값이나 과소, 과대값을 넣어서 스토리를 만들어주세요.

3. 또한 "지금 컴포넌트에 구현되어있지 않은" 동작이라 할지라도 (ex: 에러 fallback UI라던가 로딩중 UI라던가) 충분히 발생 가능한 스토리도 만들어두세요. 

4. onClick, onChange등의 콜백이 있거나 상호작용이 가능한 컴포넌트의 경우 상호작용 테스트도 구축해주세요

5. sm-, md- 나 그외 화면 크기에 따른 보여지는 모습이 달라질 가능성이 존재하는 경우, 반응형 ui 테스트를 구축하세요

6. 각 스토리 또는 상호작용 테스트마다 코드 주석으로 어떤 스토리 또는 상호작용을 테스트하고 있는 것인지 간략하게 설명을 적어주세요. 

7. 마지막으로, 이러한 스토리북을 실제로 storybook을 켠 뒤 제대로 의도된 대로 렌더링이 되는지 까지 확인하세요. 3번의 케이스도 포함하여, 제대로 렌더링이 되지 않은 케이스를 지적해서 최종 응답시 알려주세요.




## E2E 테스트 생성 규칙

E2E 테스트 코드 생성을 요청받으면 다음 절차를 따르세요.

### 1. 테스트 목표 분석
- 사용자가 검증하고자 하는 기능과 기대 결과를 파악하세요.
- 소스코드와 요구사항을 참고하되, 실제 사용자 흐름을 코드만으로 추측해 확정하지 마세요.
- 검증 조건(Assertion)이 불분명하면 사용자에게 질문하세요.

### 2. 실제 브라우저 조작
- Playwright MCP 등의 브라우저 조작 도구를 활용해 실제 애플리케이션에 접속하세요.
- 사용자가 지정한 목표를 달성하기 위해 브라우저를 직접 조작하세요.
- 클릭, 입력, 페이지 이동 등 사용자 행동을 순서대로 수행하세요.
- 조작 과정에서 실제 UI 상태와 실행 결과를 확인하세요.
- 브라우저를 조작하면서 E2E 테스트를 생성하세요.
- **요약 : 접근이 불가능하거나 사람의 개입이 필요한 단계는 사용자에게 요청하세요.**

진행 중 CAPTCHA, OTP, 외부 인증, 접근 권한 문제 등으로 직접 수행할 수 없는 작업이 발생하면 다음 규칙을 따르세요.

1. 임의로 우회하거나 실패 처리하지 마세요.
2. 사용자에게 현재 상황과 필요한 수동 조작을 설명하세요.
3. 작업을 중단하고 사용자 응답을 기다리세요.
4. 사용자가 완료했다고 알려주면 브라우저의 현재 상태를 다시 확인하세요.
5. 이후 남은 사용자 흐름을 계속 수행하세요.
6. 수동 개입이 있었던 단계는 별도로 기록하고, E2E 자동 실행 시 어떻게 처리할지 보고하세요.


### 3. 행동 기록 및 분석
- 실제 수행한 행동의 순서, 대상 요소, 실행 결과를 기록하세요.
- 각 단계에서 사용한 선택자와 화면 상태를 확인하세요.
- 안정적인 선택자(role, label, test-id 등)를 우선 사용하세요.
- 민감한 정보는 기록하지 말고 환경변수나 테스트 전용 데이터로 대체하세요.

### 4. E2E 테스트 코드 생성
- 실제로 관찰하고 수행한 사용자 흐름을 기반으로 Playwright 테스트 코드를 작성하세요.
- 단순히 클릭 순서를 재현하는 것이 아니라, 각 단계에서 중요한 상태 변화와 최종 기대 결과를 Assertion으로 검증하세요.
- 테스트 간 상태가 공유되지 않도록 독립적으로 구성하세요.
- 고정된 sleep이나 불필요한 timeout을 사용하지 마세요.
- 테스트 데이터 준비와 정리 과정을 고려하세요.

### 5. 테스트 실행 및 검증
- 생성한 E2E 테스트를 실제로 실행하세요.
- 실패하면 Trace, Screenshot, Console, Network 기록을 확인하고 원인을 분석하세요.
- 서비스 코드 결함과 테스트 코드 결함을 구분하세요.
- 테스트를 통과시키기 위해 검증 조건을 임의로 완화하지 마세요.
- 필요하다면 테스트를 수정하고 다시 실행하세요.

### 6. 결과 보고
다음 내용을 한국어로 보고하세요.

1. 테스트 대상 및 검증 목적
2. 실제로 수행한 사용자 흐름
3. 생성한 테스트 파일 및 주요 Assertion
4. 테스트 실행 결과
5. 확인하지 못한 부분과 남아 있는 위험

실제 브라우저를 조작하지 못했다면 코드 분석만으로 테스트를 생성했다는 사실을 명시하고, 실행 검증을 완료했다고 주장하지 마세요.



## E2E 테스트 실패 분석 및 수정

Playwright E2E 테스트가 실패하면 다음 절차를 따르세요.

### 1. 실패 정보 수집
- 실패한 테스트명과 에러 로그를 확인하세요.
- Playwright의 Trace, Screenshot, Video가 존재하면 함께 분석하세요.
- 실패 시점의 DOM Snapshot, Network 요청, Console 오류를 확인하세요.
- 기록이 없다면 테스트를 재실행해 필요한 정보를 수집하세요.

### 2. 원인 분석
수집한 정보를 바탕으로 실패 원인을 다음과 같이 분류하세요.

- **서비스 코드 결함**: 실제 기능이 요구사항대로 동작하지 않음
- **테스트 코드 결함**: UI 변경, 잘못된 선택자, 부적절한 Assertion 등
- **환경 문제**: 네트워크, 인증, 테스트 데이터, 외부 서비스 등
- **불안정한 테스트(Flaky Test)**: 비동기 타이밍, 상태 공유, 실행 순서 의존성 등

추측만으로 원인을 확정하지 말고, 확인한 증거를 제시하세요.

### 3. 수정
- 서비스 코드 결함이면 서비스 코드를 수정하세요.
- 테스트 코드 결함이면 테스트 코드를 수정하세요.
- 환경 문제라면 원인을 설명하고 필요한 환경 수정을 제안하세요.
- Flaky Test라면 근본 원인을 해결하세요. 임의의 sleep이나 timeout 증가로 해결하지 마세요.

테스트를 통과시키기 위해 Assertion을 삭제하거나 검증 조건을 완화하지 마세요.

### 4. 재검증
- 수정한 테스트를 다시 실행하세요.
- 가능하다면 반복 실행하여 결과의 일관성을 확인하세요.
- 수정으로 인해 기존 기능이 손상되지 않았는지도 확인하세요.

### 5. 결과 보고
다음 내용을 한국어로 정리하세요.

1. 실패한 테스트
2. 실패 원인 및 근거
3. 수정한 파일과 변경 사항
4. 재실행 결과
5. 남아 있는 위험 또는 추가 확인 사항

Trace나 실행 기록을 확인할 수 없었다면 해당 사실을 명시하세요.
