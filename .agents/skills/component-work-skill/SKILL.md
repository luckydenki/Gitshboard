## 지침

기본적으로 컴포넌트 및 UI 변경은 아래 책임 기준에 따라 컴포넌트를 구현 및 점검하세요.

참고로 기본적으로 컴포넌트 구현 및 수정은 `component-worker`가, UX 점검과 피드백 작성은 `uiux_reviewer`가 담당하며, 점검과 피드백 전달은 `docs/UIUX-guide.md`를 따르세요.


## 책임 범위

작업 규모	| 권장 실행 방식
--- | ---
문구, 색상, 간격 변경	| 메인 직접 처리, ux 점검 불필요, 피드백 없음
기존 컴포넌트의 작은 기능 변경	| 메인 직접 처리, ux 점검 불필요, 피드백 없음
단일 컴포넌트 추가 |	메인 + ux worker 호출, 피드백 1회로 제한
여러 컴포넌트 연계 변경	| component worker + uiux_reviewer 호출, UX 피드백 최대 2회로 제한
새로운 페이지 및 사용자 흐름 구현	|component worker + uiux_reviewer 호출, UX 피드백 최대 2회로 제한
인증·결제 등 중요한 사용자 흐름	강화된 검증 루프 | 	component worker + uiux_reviewer 호출, UX 피드백 최대 3회로 제한


## 피드백 루프

1. `component_worker`가 구현을 완료하면 `uiux_reviewer`가 1차 점검을 수행합니다. 메인 에이전트는 피드백을 검토하고 수정 필요성을 판단합니다.

2. 다음 조건 중 하나라도 만족하면 피드백 루프를 즉시 종료합니다.

- 수정이 필요한 문제가 없음
- 발견된 문제가 요청 범위와 무관함
- 경미한 시각적 개선 제안만 존재함
- 추가 점검으로 얻을 실질적인 이익이 적음

기능 오류, 주요 UX 결함, 접근성 문제 등이 발견되면 `component_worker`에 수정을 요청합니다.

3. 메인 에이전트는 `uiux_reviewer`에게 현재가 몇번쨰 피드백 루프인지 알려주셔야 합니다.

3. 1차 수정 후 `uiux_reviewer`는 수정된 항목만 재점검합니다. 이를 위해 메인 에이전트는 다음의 정보를 넘기세요

- 이전에 발견된 문제
- 수정된 파일
- 수정 내용
- 재현 및 확인 방법


4. 최초 점검을 포함해 UX 점검은 최대 3회로 제한합니다. 최대 횟수에 도달하면 미해결 문제를 보고하고 종료합니다.

최대 3회는 반드시 수행해야 하는 횟수가 아니라 **허용되는 상한**입니다. 기본 목표는 1회 점검으로 종료하는 것입니다.




## 증분 UX 점검

1. 최초 점검에서는 변경된 사용자 흐름 전체를 검증하세요.

2. 2차 점검부터는 이전에 발견한 문제와 수정된 코드의 영향 범위만 검증하세요.

메인 에이전트는 재검증을 요청할 때 다음 정보를 전달해야 합니다.

이전에 발견된 문제

수정된 파일

수정 내용

재현 및 확인 방법

이전 점검에서 정상으로 확인된 항목은 수정으로 영향을 받지 않았다면 다시 점검하지 마세요.

중대한 문제가 없다면 추가 개선점을 찾기 위해 점검을 반복하지 마세요.


## 예외
1. 사용자가 대놓고 **"간단하게"** 와 같은 간단함을 나타내는 수식어를 썼거나 명시적으로 **worker들을 호출하지 마라고 했을** 경우 **메인 에이전트가 직접 수정해야 합니다.** 

2.  만약 **사용자가 직접 피드백 루프 횟수를 지정했다면 그것을 우선시 하세요.**
