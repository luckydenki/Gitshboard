# Git Convention


## 커밋 양식

1. commit -m 으로 작성할 것

2. 커밋 메세지 길게 쓰지 말고 핵심만 적을 것. 총합 최대 100글자 내외로.

3. 되도록이면 최대한 잘게 쪼개어 커밋할 것

4.`[커밋 타입] : 수행한 일` 로 작성하면 됨. 그외 제약사항은 없음.


이렇게 하는 이유는 커밋 양식에 메달려서 개발이 지나치게 지연되는 일을 방지하기 위함.

다만 만약 ai 커밋 자동화가 수월해진다면 차후 양식을 좀 더 디테일하게 만들예정.



## 커밋 타입 규칙

| 말머리  | 설명 |
| --- | --- |
`feat` | 새로운 기능 추가
`fix` | 기능 수정 또는 버그 수정
`design` | 레이아웃, 마크업, css 디자인 수정
`refactor` | 리팩토링 
`config` | config류 파일들의 설정 변경
`install` | npm 의존성 추가 또는 설치
`uninstall` | npm 의존성 삭제
`test` |  테스트 파일 작성 또는 테스트 목적으로 작성한 코드나 작업 (storybook도 전부 test로 작성함)
`restruct` | 파일 구조 변경
`remove` | 파일 또는 폴더 삭제
`add` | 파일 또는 폴더 추가
`rename` | 파일 또는 폴더 이름만 변경
`docs` | md 파일류의 문서 파일 작성,메서드, 변수 등에 설명 주석을 달아놓는 일.
`chore` | 말 그대로 위 내용으로 표현하기 어려운 그외 잡일 (주석 제거, 쓸데 없는 변수나 함수 제거, 오타 수정 등)
`wip` | work in progress, 아직 작업 중인데 중간 저장을 위해 사용하는 케이스
`hotfix` | master 브랜치에 직접 수정 사항을 반영해야 하는 급한 일.

1. 되도록 wip는 남발하지 말것
2. 실수로 여러 개의 작업을 동시에 했다면 + 로 묶어서 표현하고, 각각에 대해 어떤 작업을 했는지 commit message에 1, 2.. 같은 번호로 남기기
3. 기능 추가를 하는 과정에서 코드 구조가 좀 변했다고 해도 feat로 처리하셈.
4. 이해 편하라고 config 류라 했지만 그냥 프로젝트의 설정을 변경한다는 느낌이면 전부 config로 처리함. 가령 package.json 설정 변경, gitignore 추가 등도 전부 config에 포함


## 브랜치 규칙

1.브랜치 타입은 feat, fix, refactor, test로 나뉘며 **반드시 master에서 파생시켜야 함**

2. 굳이 엄격하게 나눌 필요는 없으며 애매하면 그냥 feat로 할 것

3. 브랜치 명은 `브랜치타입/기능이름` 으로 작성하면 됨.

4. 띄어쓰기는 스네이크 케이스로 쓰셈



## 브랜치 전략

github flow를 사용함. git flow를 사용하지 않는 이유는 다음과 같음.

1. 1인 개발이라 모든 코드를 혼자 통제하고 제어함. 협업에서는 충돌 방지 등의 이유가 있지만 1인 개발인 이상 그러한 위험이 매우 적음.

2. 굳이 git flow를 연습한다는 명목으로 그러한 이력서 주도 개발 전략을 짜고 싶지 않음. 필요하면 차후 develop 브랜치를 개설하여 일종의 대비책 브랜치를 만들어 둘 것임.


크게 구조는 이러함.

1. master 브랜치
실제 배포 브랜치이며, 모든 브랜치는 master 브랜치에서 파생하고 master 브랜치에 직접 병합함.

master 브랜치에 `직접` 올려야 하는 경우, 모든 커밋은 전부 `!hotfix`를 달고 커밋하면 됨.


2. feat, refactor, test, fix 브랜치

각각 기능 추가, 리팩터링, 테스트, 수정을 목적으로 하는 브랜치임. 용도에 맞게 브랜치명을 지으면 됨.

다만 그 용도에 타이트하게 사용할 필요는 없다고 정하겠음. 타이트하게 하는 습관을 들이는 게 좋겠지만, 

1인개발이라 코드가 어떻게 돌아가는 지 전부 다 알기 때문에 완전히 독립적으로 짜지 않아도 리스크 방지는 충분하다고 느낌.



## PR, 이슈 양식

- 차후 PR, 이슈 자동화를 작업하게 될 때 작성할 예정.


## 주의사항

1. 매 push 마다 반드시 빌드 테스트를 해야 하며, 10 커밋마다 한번씩은 푸쉬하는 것을 권장

2. **hard reset, force push, pull은 절대 사용하지 말 것**
