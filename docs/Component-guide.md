# COMPONENT GUIDE ( 6.1 Terra 모델)

컴포넌트 구현 또는 수정을 요청할 시 다음과 같은 기본 규칙을 따르세요

## 기본 규칙

- 컴포넌트 하나당 하나의 파일을 사용하는 게 원칙입니다. 이 경우 `export default function` 문으로 작성하세요
- 같은 파일 내에 별도의 UI 컴포넌트를 추가해달라고 한다면 `export const` 화살표 함수로 작성해주세요. 반드시 메인 컴포넌트인 `export default function`보다 위에 작성하셔야 합니다.
- 하나의 패널, 메뉴, 영역은  section 또는 article로 시작할 수 있도록 해주세요. (단 네비게이션의 nav, 사이드바의 aside는 예외)
- 모든 태그는 최대한 시멘틱하게(의미에 맞게) 사용하세요. 단, 드롭다운과 같이 디자인에 제한이 되는 태그는 다른 방식으로 구현해도 상관 없습니다.
- 만약 새로운 컴포넌트를 구현하게 된다면, 그와 관련된 **스토리북** 스토리를 생성하세요. 스토리북 규칙은 frontend AGNETS.md를 참고하세요.
- 만약 구현 또는 수정하게 되는 컴포넌트와 관련된 **스토리북**이 이미 있다면, 그와 관련된 mock, 타입, 스토리북 파일도 수정된 버전에 맞게 업데이트 시켜주세요.


## 컴포넌트 분리

1. 컴포넌트 분리는 후술할 예외를 제외하면 바로 분리 하지 말고 파일 하나 내에서 전부 구현해주세요
2. 임시적인 mock 데이터는 반드시 /mock 폴더로 분리하세요. 보통은 페이지 단위로 폴더를 만들어 분리를 권장합니다.(중첩 라우팅의 경우에도 중첩된 폴더를 만들어 관리하면 됨)
3. 컴포넌트를 너무 원자적으로 분리하지 마세요. 응집도를 위해, 매우 의존성이 높은 컴포넌트라면 하나의 파일 안에 담으세요.
ex) 리스트와 리스트 아이템은 그 의존도가 굉장히 강하니 하나의 파일 안에 넣기를 바랍니다.
4. 위 작업을 모두 마친 후에도 줄 길이가 300줄 이상 넘어가는 컴포넌트가 있다면 **별다른 지시사항이 없어도** 곧바로 분리작업을 시작하세요. 이 때 `section`과 `article`단위로 분리시키고, 그 외의 분리시키는 방식은 추가적인 지시가 있지 않다면 분리하려는 방식에 허가를 받도록 하세요


## components 폴더

- 대부분의 컴포넌트들은 components에, 라우팅에 직접 연결된 페이지 컴포넌트는 (단 중첩 라우팅은 제외) routes에 두세요
- common : 공통 컴포넌트들입니다. 그냥 두 페이지 이상의 곳에서 사용되었다면 이쪽에 넣어두세요
- page : 페이지 컴포넌트들입니다. 해당 페이지에서만 유일하게 사용되는 컴포넌트들은 이쪽에 넣어두세요
